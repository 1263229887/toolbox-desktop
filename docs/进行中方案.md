## 图片去水印：已整体移除（2026-10-08）

用户实测后判定成品观感不值得为它维护一整套模型分发/推理链路，插件、检测层、
MI-GAN 模型包、阿里云云端增强、utilityProcess worker 与相关自检已全部删除。
**调研结论留档如下，避免下次重新讨论一遍：**

- **修复层不是瓶颈**：同一张样张、同一份 mask、PSNR 口径下 MI-GAN 28MB = 24.37dB，
  LaMa 198MB = 24.11dB，原图基线 20.05dB。换更大的修复模型换不来质变。
- **端到端指令编辑模型不可行**：Qwen-Image-Edit(20B)/BAGEL(7B)/Step1X-Edit/OmniGen2
  最小量化档 6~14GB，官方最低显存 12~17GB，全表零 CPU 实测证据；扩散 20~50 步在无 GPU 机器必 >1 分钟。
- **国产开源 VLM 做检测也不可行**：`Qwen2.5-VL-3B` 的 LICENSE 实测是 **非商用**；
  能商用的最小 Apache VLM 是 Qwen3-VL-2B / MiniCPM-V-4.6，但 llama.cpp issue #27649 一手数据是
  0.8B 模型纯 CPU 单图 ~30 秒（瓶颈在 vision encode），且 #13694/#29251 记录量化后 bbox 精度不保；
  WASM 根本跑不了自回归 VLM。
- **没有 <100MB 且 Apache/MIT 的水印/logo 检测权重**：YOLO-World 实测 **GPL-3.0**（桌面 App 传染）、
  ultralytics AGPL-3.0、GroundingDINO tiny ONNX 227~719MB、MAT 权重 **CC-BY-NC-4.0**。
- **主流产品形态是"自动 + 可编辑选区"**（佐糖产品页原文），连 Florence-2 1.8GB 都有 issue 记录
  密集平铺水印除不掉。所以"一键"的瓶颈在检测，不在模型大小。
- **付费云端确实便宜**：阿里云 `RemoveImageWatermark` 0.01 元/次、每月 100 次免费、失败不计费、
  全自动不需要传 mask；且**不需要自建中转或 OSS 桶**（新版 SDK 的 `xxxAdvanceRequest` 直接吃本地文件流）。
  唯一门槛是 AK/SK 归属——不能进公开安装包，只能用户自填或加一层服务端。
  千问 `image-erase-completion` 要原图+擦除mask+保留mask 三个输入、500 张免费后不可续，不是无感一键。
- 踩过的技术坑留档：LaMa ONNX 要 `v/255`（不是 `-1~1`）、mask `1=洞`、输出已是 0~255、mask 需膨胀 ~6px；
  矩形框 mask 会让模型重绘完好背景（正解是框内取笔画 + 膨胀）；ort-web 的 `ort.node.min.mjs` 不自包含，
  要连 `onnxruntime-common` 一起打包；路径里含 `node_modules` 的解压会被 Electron 的 asar fs 拦截，
  需 `process.noAsar = true`。

## 与 vd.aisoup.ai 的对比 + 批量解析可行性（2026-10-10 实测）

样张：`https://v.douyin.com/nxl054Q9i3s/`（30s 视频，作者「不太明白」）。

### 对方不是同一套方案

扒了它的 `static/script.js`：`/check-env` 直接回 `{ytdlp_installed:true}`，还有 `/install-ytdlp`、`/download-jobs`
——**它是服务端跑 yt-dlp 的网页壳**。yt-dlp 的抖音抽取器在 `yt_dlp/extractor/tiktok.py` 的 `DouyinIE`：

```python
detail = self._download_json('https://www.douyin.com/aweme/v1/web/aweme/detail/', query={'aweme_id': id}, fatal=False)
if not detail:
    raise ExtractorError('Fresh cookies (not necessarily logged in) are needed', ...)
```

也就是它要靠**服务器上的 cookie 池**打抖音的 web detail 接口，拿到 `video.play_addr.uri` 之后拼出那条经典无水印端点：

- 它返回的地址：`https://aweme.snssdk.com/aweme/v1/play/?video_id=v0200…&ratio=720p&line=0`
- 本机裸 curl（无 UA / 无 cookie / 无 Referer）实测：1 跳 302 → `*.douyinvod.com` → `206 video/mp4`，TTFB 0.36s
- `ratio` 可给 `1080p`：同一条视频 1080p=3.83MB、720p=2.89MB、540p=2.71MB（它默认只给 720p）

**这条 play 端点本身不需要任何凭证**，卡点全在「怎么拿到 `video_id`」。本机实测两条路都不通：
web detail 裸请求回 `403 Blocked by ArgusSecurityPlugin Uifid Not Found`；Googlebot 抓 `/video/` 页面 96KB 里
`v02…`/`play_addr`/`douyinvod` 全为 0。所以**这个技巧没法在纯客户端复刻**，我们没有换掉现有链路的技术理由。

### 速度：我们更快，而且少一跳

| | 解析耗时 | 流来源 |
|---|---|---|
| vd.aisoup.ai | 4.3s | 它的服务器 `/download-jobs` 代下再回传（两跳） |
| 本项目 demoApi 层 | 1.9～2.9s | 直连 `zjcdn.com`，渲染进程/主进程自己下（一跳） |
| 本项目 seo 层（视频） | 1.7s 后判失败 | 设计上视频就不走这层，会落到 demoApi |

本机直连那条 CDN 实测 3.83MB / 6.4s ≈ 0.57MB/s（慢是链路慢，不是方案慢；对方代下同样吃这条链路，还多一跳）。

### 作者维度批量下载（2026-10-10 已实现）

入口两条，都弱化，主路径仍然是粘分享链接：

1. 解析成功后，结果头部一个次要按钮「查看 TA 的其他作品」——**不额外发请求**：
   demoApi 那条链路本来就把完整 `author` 对象（`sec_uid`/`web_url`/`unique_id`/`nickname`）回给我们了，
   之前只取了昵称白白扔掉。现在 `parse()` 的 `author` 是对象（`douyin.js` 里注释了原因）。
2. 输入框下方「按作者主页链接批量拉作品」，只认主页链接。

拿到列表后是**勾选式**（默认不选任何一条），确认后才建队列。

**关键前提（实测）**：`GET /api/v1/{platform}/user/posts?url=…|sec_user_id=…&count=&cursor=`
一次调用就把每条的无水印直链一起带回来看：`count=20` → 22 条、`has_more:true`、`cursor` 是毫秒时间戳，
每条自带 `content_id`/`web_url`/`title`/`stats`/`music`/`duration_ms`/`created_at` + `media.streams[]`
（13 路，**全部 `watermark:false`**，最高 1080x1440）。
→ **批量不需要逐条再 parse**，一次批量 = 1 次列表调用 + N 次 CDN 下载，公共 demo 站几乎没压力。
同族还有 `user/likes`、`user/reposts`、`user/collections`、`mix/posts`（合集）、`tools/parse-batch`。

**上游风控契约（这条是实测踩出来的，比任何延时策略都重要）**：
连着两次 `user/posts` 就会被判自动化流量 ——
`{"code":"UPSTREAM_RISK_CONTROL","message":"平台判定该请求为自动化流量，相关身份已进入冷却。","retryable":true,"retry_after":60}`。
所以：

- 对面是**每身份 + 每端点的令牌桶 + 端点熔断**（v5 README 明写），不按累计条数封人。
  因此**不做「按序号递增延时」**（第 40 条硬等 40 秒那种自我惩罚），改成
  **固定基础间隔 + 拿到 `retry_after` 就照它说的秒数冷却**（`ipc.js` 的 batch 循环，封顶 180s）。
- 列表按钮「再加载 20 条」失败时不清空已有列表，只在旁边报一句话（`AuthorWorks.vue` 的 `listError`）。
- `douyin.js` 里 `UpstreamRisk` 把 `code`/`retryAfter` 带成 Error 字段，主进程据此退避。

**队列形态的三条硬约束**：

- **直链只有约 3 小时有效期**（实测签发 `09:43:31Z` → 过期 `12:44:01Z`；路径里那段 8 位 hex 就是过期时间戳。
  图文原图是 30 天，差一个数量级）。所以**不能「先解析完 N 条再慢慢下」**，一条下完再进下一条；
  失败时只重新解析这一条，不回头刷整个列表。
- **串行不并发**：批量真正打的是抖音自家 CDN，个人用量下多路并发省不了多少时间，
  却要把进度归属和 CDN 侧异常判定都再处理一遍。
- 一条图文可能有十几张图，中途失败按下标记住已落地的（`landed`），重试只补剩下的。
  取消走 `AbortController`，`netio.downloadFile` 收到 abort 不再当网络抖动重试。

**「给一个抖音号能不能直接拉全部作品」→ 不能**，六条路都堵死（用真实抖音号 `yaoyao373733` 试的）：

| 路子 | 结果 |
|---|---|
| `www.douyin.com/user/<抖音号>` + Chrome UA | 回 72914 字节的 `_$jsvmprt` **JS 虚拟机风控页**，无数据 |
| 同上 + Googlebot UA | `200`，**0 字节** |
| `iesdouyin.com/share/user/<id>`、`m.douyin.com/share/user/<id>` | 同一个 VM 风控壳，字节数一模一样 |
| demo 站 `user?url=` / `user/posts?url=` 喂该链接 | `state: failed` |
| DuckDuckGo 反查索引里的主页链接 | 本机不可达（`http=000`） |
| Bing 反查 `site:douyin.com <抖音号>` | 有 SERP，但结果里没有 `user/MS4w…` |

根因：demo 站那 88 个端点里**没有任何 search 端点**，纯文本号换不成 `sec_uid`。
反过来 `unique_id`（抖音号）是白送的 —— 只要有一条作品链接或主页链接，`author.unique_id` 就在响应里。
所以界面把话说明白：只认主页链接，粘抖音号会直接告诉你为什么不行。

### PDF 相关的坑（写进 ops.js 注释，别再踩）

- pdf-lib 内部用 `new DataView(bytes.buffer)` 读 JPEG，**传 Buffer 会踩内存池**（`.buffer` 起点非 0），
  报「SOI not found in JPEG」；必须给独立的 `new Uint8Array(...)`。
- 换图后必须同步 `/Length`，并按 JPEG SOF 更新 `/Width`/`/Height`，否则阅读器按旧长度截断。
- 压缩要判「越压越大就跳过」，否则低质量原图会被反噬。
- `setSubject(undefined)` 会被 pdf-lib 校验器拒（要求 string），清空属性只能写空串。
- **旋转对象只有一个合法形状：`degrees(n)` 造出来的 `{type:'degrees', angle}`**（`api/rotations.js`）。
  自己拼 `{type:'deg', value:n}` 会在 `toRadians()` 里抛 `Invalid rotation: {"type":"deg","value":-45}` ——
  `core` 里那套 `AngleTypes` 是 `'deg'`，和 `api` 层的 `RotationTypes` 不是同一个枚举，别照抄。
  平铺水印的 `drawImage({rotate})` 就栽在这：`check-pdf` 当时只测了 `tilePositions` 的格子数，没真跑 `drawImage`。
- 回归脚本 `tools/check-pdf.mjs`（26 项）已补「非 0 倾角真的走一遍 drawImage」+「预览矩阵逐点对齐 pdf-lib 画法」，
  PDF 相关改动务必跑它。用旧写法反跑一次能复现报错，确认这条断言不是摆设。

### PDF 预览（2026-10-09）

渲染层用 **pdfjs-dist 6.4.299（Apache-2.0）**，只负责「把页画出来」；改写 PDF 仍然全部是 pdf-lib，两边互不依赖，
所以预览挂了不影响导出。水印预览不是另画一套近似效果：`placementXY` / `tilePositions` / `stampMatrix`
和导出时是同一批函数、同一张 overlay 图源，屏幕所见即落盘所得。

实测过的 Electron 44 加载事实（`/tmp` 里起了个一次性窗口验的，不是推断）：

| 路径 | 结果 |
|---|---|
| `new Worker(blobURL, {type:'module'})` 于 `file://` 页面 | ✅ 可用 → worker 源码用 `?raw` 内联后转 blob |
| `new Worker('file:///...mjs', {type:'module'})` | ✅ 也能用，但要赌 asar 内的 worker，没走这条路 |
| 动态 `import('file:///...mjs')` | ✅ 可用（Vite 的懒加载 chunk 在打包后靠这个） |
| pdfjs 默认 `workerSrc` 走 URL 解析 | ❌ 不用：`_createCDNWrapper` 会再包一层 blob 去 import `file://`，asar 下不稳 |

- 喂给 pdfjs 的字节必须 `.slice()`：它会把 ArrayBuffer transfer 给 worker，同一份 bytes 再给 pdf-lib 就空了。
- `viewport.transform` 自带 y 翻转（实测 `[1.5,0,0,-1.5,15,877.91]`），所以预览矩阵直接左乘它就能对上 PDF 坐标。
- **没打包 `cmaps/` 与 `standard_fonts/`**（约 4MB）。实测中文报关单能正常出字（这类 PDF 字体是内嵌的）；
  真遇到「非嵌入 CJK 字体 + 预定义 CMap」的老 PDF，预览可能缺字，但导出结果不受影响。
  要补的话就是 cmaps 目录 + `CMapReaderFactory`（file:// 下 `fetch` 不通，得走 IPC 读 asar）。
- 体积代价：`out/renderer` 多了约 2.9MB（pdf 主模块 1.64MB + worker 字符串 1.27MB），且是首次预览才加载的懒 chunk。
- 缩略图走 `serialize()` 串行队列：pdfjs 解析在 worker，但**画布绘制在主线程**，几十页同时渲染会直接钉住界面。

### 有没有现成的 PDF 编辑库可换（2026-10-09 调研）

结论：**不换**。pdf-lib 该继续用，缺的能力是「渲染」而不是「编辑」，已经用 pdfjs 补上了。

- **@cantoo/pdf-lib**（MIT，活跃，API 与 pdf-lib 兼容）：支持 `.ttc` 字体集合 + `postscriptName`，
  是目前唯一能正面解决「中文矢量文字」的开源路子。真要上，还得配 `subset-font` 把字体裁成几百 KB 的子集。
  现在的 canvas→PNG 方案在 300dpi 打印下不糊，先不换。
- **EmbedPDF**（Vue 官方 viewer 包，PDFium WASM）：viewer/批注/真涂销很强，但 v3 自己标了 not production，
  且是 viewer 定位，替不掉 headless 的合并/拆分/压缩管线。
- **vue-pdf-embed / @tato30/vue-pdf**（MIT）：只是 pdfjs 的薄封装，卖点就是它已经把 blob worker 那套坑踩平了。
  我们自己踩的坑更短（一个 `?raw` + 三行），不引它。
- **Nutrient(原 PSPDFKit) / Apryse / Foxit**：唯一开箱即用的完整编辑器 SDK，都支持离线自托管，
  但都要买 license key 且价格不公开 —— 与「免费 + 安装包小」直接冲突。
- Word→PDF 离线可做（mammoth 解析 + `webContents.printToPDF()`）；PDF→Word 仍然不建议（见上面第 6 条的口径）。
