### 修复层实测（2026-09-30，同一张样张、同一份 mask）

样张：`~/Pictures/待去水印` 第一张，砂石泡沫高频纹理上的半透明白色「抖音号：xxx」。
指标：水印带与手工成品的 PSNR（越高越接近人工结果）。

| 方案 | PSNR | 观感 |
|---|---|---|
| 原图（基线） | 20.05 dB | — |
| MI-GAN 28MB（当前） | **24.37 dB** | 水印干净消失，纹理略平滑 |
| LaMa 198MB（正确用法，mask 膨胀 6px） | 24.11 dB | 同样干净，颗粒感略好一点点 |

结论：**修复层不是瓶颈**，换 LaMa 换来的是 7 倍体积 + 边际观感差异，不值。
「一键」卡在检测层。

LaMa(Carve/LaMa-ONNX) 的正确用法（之前两次误判都源于此，别再踩）：
- 输入 image：float32 `[1,3,512,512]`，归一化 **`v/255`（0~1）**，不是 `-1~1`；喂错会出墨绿色涂抹（9.8dB）
- 输入 mask：float32 `[1,1,512,512]`，**1 = 待修复**
- 输出：**已经是 0~255**，不要再乘 255
- mask 膨胀 ~6px 最佳（0px 留边缘残影，12px 反而变差）
- 复现脚本：`tools/bench/lama-calibrate.mjs`

### 检测层实测（2026-09-30，7 张真样本，`tools/bench/detect-recall.mjs`）

真值 = 「待去水印」与「已去水印」两张图的差分（阈值 60、膨胀 5px），不靠人工标注。

| 口径 | 召回 | 误伤 | 耗时 |
|---|---|---|---|
| 原启发式（只认「水印会提亮」） | 5/7 = 71% | 0 | 70ms |
| 放宽为亮度差取绝对值 + 笔画高频 | 6/7 = 86% | **6 个框** | 70ms |
| **只自动应用分数最高的 1 个框**（采用） | 6/7 = 86% | **0** | 70ms |

两个结论写死在代码注释里：
- 白字压近白背景时亮度差只有 ±2，**方向不定的**，只测正向提亮必漏检；
- 「默认直接修」的东西绝不能误伤，所以自动应用范围收窄到首选框，其余作为可勾选候选。

### 能不能靠大模型做到「一步到位」：三路调研结论（2026-09-30）

**结论：不能，而且这不是模型先进与否的问题。**

1. **端到端指令编辑模型全部出局**（Qwen-Image-Edit 20B / BAGEL-7B / Step1X-Edit / OmniGen2）：
   最小量化档也要 6~14GB，官方最低显存 12~17GB（OmniGen2 README 原文要求 RTX 3090 + 17GB VRAM），
   **全表零 CPU 实测证据**；扩散要 20~50 步去噪，无 GPU 必 >1 分钟。
   而且它并没有省掉「哪里是水印」这一步，反而从两段变三段。
2. **国产开源 VLM 做检测也不可行**，四个独立卡点：
   - **许可**：`Qwen2.5-VL-3B` 的 LICENSE 原文是「Qwen RESEARCH LICENSE AGREEMENT … FOR
     NON-COMMERCIAL PURPOSES ONLY」——能商用的最小 Apache VLM 只有 Qwen3-VL-2B / MiniCPM-V-4.6；
     DeepSeek-VL2 是自定义 LICENSE-MODEL（条款向下传染），Hunyuan 是腾讯社区许可（排除欧盟/英美/韩 + MAU 阈值）。
   - **CPU 延迟**：llama.cpp issue #27649 一手数据——骁龙 8 Elite 8 核、**0.8B** 模型、单张图端到端
     **~30 秒**（瓶颈在 vision encode）。比修复层慢两个数量级。
   - **体积**：视觉投影器压不进小包，Qwen3-VL-2B 的 Q4_K_M 1107MB + mmproj 445MB ≈ 1.55GB 起。
   - **精度**：#13694「Qwen2.5-VL-7B returns extremely inaccurate bbox coordinates」、#29251 视觉
     embedding 精度噪声——量化后框本身就不准。WASM 更是跑不了自回归 VLM（4-bit 权重/external data 都不支持）。
3. **没有「<100MB + Apache/MIT + 能检出右下角半透明 logo+文字」的检测模型**：
   GroundingDINO 代码 Apache 但 tiny ONNX 也要 227~719MB；YOLO-World 实测 **GPL-3.0**（比 AGPL 更糟，
   桌面 App 有传染风险）、ultralytics 系 AGPL-3.0；现成水印检测权重要么 AGPL 要么「academic only」要么无 LICENSE；
   MAT 是 **CC-BY-NC-4.0** 商用不可用。
4. **主流产品形态也不是"纯自动"**：佐糖产品页原文是「自动检测并清除所有水印」**＋**「如果需要更精确的控制，
   也可以使用手动笔刷标记并清除」。连 Florence-2(1.8GB) 都有 issue #56 记录「密集平铺 SAMPLE 水印除不掉」。
   → 所以「自动 + 可编辑选区」不是妥协，是这个问题的正确形态。

### 免费 / 付费 API

- **不存在**「免注册、长期免费、且允许嵌进第三方 app」的通用去水印 HTTP API。
  阿里云每月 100 次免费；腾讯云数据万象「图像修复」是 1000 次 / 2 个月**一次性**额度；
  watermarkremover.io 注册送 3 次、HD 输出要付费。
- 项目内 `nologo.code24.top` 是抖音解析 token，不是通用去水印。
- **付费路线值得做**（2026-09-30 读官方文档核实）：阿里云视觉智能
  [`RemoveImageWatermark`「图像标志擦除」](https://help.aliyun.com/zh/viapi/developer-reference/api-rivr81)
  **0.01 元/次**、每月前 100 次免费、调用失败不计费，且**请求参数只有 `Action` + `ImageURL`
  即全自动、不需要传区域或 mask**，能力原文是擦「台标、互联网平台 Logo 标志」——
  正好补上本地检测层完全覆盖不了的图形 logo。另有「字幕擦除」同价、「图像人体擦除」0.06 元/次。
  限制：免费期 2QPS、买资源包后 5QPS；能力在**华东2（上海）**；返回 30 分钟有效期的临时链接。
- **不需要自建中转服务，也不需要自己的 OSS 桶**（更正：早先记的「必须公网可读 URL + 需要中转桶」是错的）。
  官方《文件URL处理》给了两条路：
  - **走这条**：新版 SDK 的 `RemoveImageWatermarkAdvance`（`xxxAdvanceRequest`）直接接受**本地文件流**，
    SDK 底层完成上传与 URL 转换；
  - 官方临时通道 `GetOssStsToken` → 共享桶 `viapi-customer-temp`（文件存 1 天），但文档原文写明
    「请勿在生产环境使用」「此上传接口不推荐付费用户使用」→ **不能用**。
- 该接口参数表里**只有 `ImageURL`、没有 Base64 参数**；平台虽有《文件Base64处理》文档，
  但只说「部分能力」支持且未列到图像标志擦除 → 别指望 base64 直传，走 Advance 流。
- **真正必需解决的只有一件事：AK/SK 从哪来。**
  - 用户自填 key（存 `userData/secrets.json`，机制已有）→ 完全直连，零基础设施，签名逻辑在官方 SDK 里；
  - 要让用户零配置、用我们自己的 key → key 不能进公开安装包，这时才需要一层服务端（限流 + 计费）。
  注意：即便走 Advance，图片仍然会上传到阿里云，只是不需要我们自己准备存储。

### 分发与网络

- 插件 zip / 模型包目前挂 GitHub Release；国内直连慢且易 `fetch failed`
- 可用镜像（实测）：`https://gh-proxy.com/https://github.com/...`（约 3～5MB/s）
- 后续若正式分发，建议同步到 Gitee Release / 国内 OSS，并把 `pluginRegistryUrl`、`modelBaseUrl` 指过去
- Node/`electron` 主进程 `fetch` **不吃**系统代理；Clash 开着反而可能更差。启动 dev 时不要带 `HTTPS_PROXY`
